𝟭. 왜 에러가 없는가?
  ZMQ는 소켓이 실제 연결되었는지 여부와 상관없이 "메시지를 보낼 수 있는 상태"를 
추상화합니다.

①  Connect 시 에러가 없는 이유: 
   ZMQ의 connect()는 즉각적인 핸드셰이크를 수행하지 않습니다. 
 백그라운드 스레드에서 재시도를 반복하므로, API 레벨에서는 항상 성공으로 
 리턴됩니다.

②  Send 시 에러가 없는 이유: 
  XPUB/XSUB는 기본적으로 비동기 큐를 가집니다. 
 Proxy가 죽어있더라도 로컬 메모리 버퍼(High Water Mark)가 가득 차기 전까지는 
 메시지를 큐에 쌓고 성공을 반환합니다.

③ Proxy 종료를 모르는 이유: 
  TCP 연결이 끊어져도 ZMQ는 이를 '일시적 장애'로 판단하고 자동으로 
 재접속을 시도합니다. 이 과정이 사용자 애플리케이션에는 은폐됩니다.

𝟮 해결을 위한 이론적 접근
①  Monitor API 활용 (연결 상태 추적)
  ZMQ는 소켓의 내부 이벤트를 모니터링할 수 있는 zmq_socket_monitor API를 
 제공합니다. 이를 통해 Proxy와의 연결이 실제로 수립되었는지(CONNECTED), 
 끊어졌는지(DISCONNECTED)를 이벤트 단위로 수신할 수 있습니다.

방법: 별도의 인프로세스(inproc://) 소켓을 통해 연결 상태 변화를 실시간으로 
      모니터링하고, 연결되지 않은 상태라면 데이터를 보내지 않고 알람을 
      발생시킵니다.

②  Heartbeating 패턴 (생존 확인) 🔴
   2~3개월간 데이터가 없는 상황이라면 TCP Keep-alive만으로는 부족합니다. 
  애플리케이션 레벨의 하트비트가 필요합니다.

  방법: XPUB/XSUB Proxy가 주기적으로 "I am alive" 메시지를 특정 토픽으로 
        발행하게 합니다. 클라이언트는 이 메시지가 일정 시간 이상 오지 않으면 
        Proxy 장애로 판단하고 세션을 재설정하거나 관리자에게 통보합니다.

③  신뢰성 있는 전달 (Reliability Patterns)
   ZMQ 가이드(Majordomo 패턴 등)에서 권장하는 방식입니다.

   Lazy Pirate 패턴:  클라이언트가 요청을 보내고 일정 시간 내에 응답(ACK)이 
                     없으면 소켓을 닫고 새로 생성하여 재시도합니다.

   확인 응답(ACK) 구조: 미션 크리티컬한 데이터라면 PUB/SUB 단방향 전송에 
                        의존하지 말고, 중요한 데이터에 한해서만 REQ/REP나 
                        별도의 피드백 채널을 통해 수신 성공 여부를 확인하는 
                        로직을 병행해야 합니다.
